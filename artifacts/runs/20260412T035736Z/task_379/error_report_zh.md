# Task 379 中文错误报告

## 一、报告目的

这份报告用于分析 `artifacts/runs/20260412T035736Z/task_379` 中模型为何提交了大量逐分子明细，而不是标准答案要求的元素汇总结果。

本题的关键失误是“输出粒度错位”：

- 题目要的是第 4 原子的毒理元素统计结果
- 模型提交成了“每个分子一行”的明细表

## 二、题目原文与中文翻译

### 题目原文

`Tally the toxicology element of the 4th atom of each molecule that was carcinogenic.`

### 中文直译

`统计每个致癌分子中第 4 个原子的毒理元素。`

### 更适合分析的中文表述

`先筛出致癌分子，再取每个分子的第4个原子元素，最后输出元素层面的统计结果。`

## 三、任务和数据集背景说明

### 1. 这是什么类型的任务

这是化学结构统计题，包含三个动作：

1. 识别 carcinogenic 分子
2. 在原子序列中定位“第4个原子”
3. 按元素做 tally（汇总）

### 2. 这个任务提供了哪些数据

`task_379/context` 主要包含：

- `doc/molecule.md`
- `csv/atom.csv`
- `knowledge.md`

#### `molecule.md`

以叙述文本给出各分子的毒理判断（含部分“先否后改”的修订语句）。

#### `atom.csv`

提供原子明细：

- `atom_id`
- `molecule_id`
- `element`

可用于按原子序号提取第 4 原子元素。

#### `knowledge.md`

给出了 molecule/atom/bond 的关系语义，支持“先筛分子，再抽取原子位次”的路径。

## 四、这道题正确的求解思路应该是什么

正确流程应为：

1. 从 `molecule.md` 稳定识别致癌分子集合。
2. 在 `atom.csv` 中按 `molecule_id` 分组，并按原子顺序定位第 4 原子。
3. 取第 4 原子的 `element` 做 tally。
4. 输出元素层面的结果（本题 gold 为元素列表）。

## 五、模型最终给出了什么答案

模型输出文件：

- `artifacts/runs/20260412T035736Z/task_379/prediction.csv`

模型输出结构：

- 列：`molecule_id, element`
- 行数：`90`

即每个分子输出一行第4原子元素，而不是元素汇总结果。

进一步检查这 90 行预测可以发现：

- 去重前：`90` 行
- 仅按 `element` 去重后：只剩 `c, cl, h, o` 这 `4` 个元素

这说明问题不只是“没做聚合”，因为即使最后补一个 `DISTINCT element`，当前结果仍然和 gold 不一致。

标准答案文件：

- `data/public/output/task_379/gold.csv`

gold 只有一列 `element`，共 7 行：

- `c`
- `br`
- `cl`
- `s`
- `o`
- `n`
- `f`

## 六、模型在 Trace 中是如何一步步出错的

### 第一步：从文本抽取致癌分子集合

trace 显示：

- 先得到 84 个候选
- 后扩展到 90 个候选

该阶段已出现文本修订语句带来的噪声累积风险。

### 第二步：工具路径有一次无效尝试

模型对 `csv/atom.csv` 调 `inspect_sqlite_schema`，报错：

- `file is not a database`

随后改回 Python 读取，继续执行。

### 第三步：第 4 原子的定位方式本身就错了

模型在 Python 中这样取第 4 原子：

```python
atoms_by_molecule[molecule_id].append(element)
fourth_atom = atoms_by_molecule[mol][3]
```

也就是说，它把 `atom.csv` 中同一分子的元素按“文件当前出现顺序”直接 append 到列表里，然后取列表下标 `3`。

问题在于：`atom.csv` 的同分子原子并不是按真正原子序号 `1,2,3,4,...` 排列的，而是按字符串顺序出现。例如 `TR001` 在文件中的开头顺序是：

- `TR001_1`
- `TR001_10`
- `TR001_11`
- `TR001_12`
- ...
- `TR001_2`
- `TR001_3`
- `TR001_4`

因此模型取到的“第 4 个原子”其实经常是：

- 第 4 条出现的 atom 记录

而不是：

- 原子编号后缀为 `4` 的 atom

这会直接把大量分子的第 4 原子元素取错。

### 第四步：由于原子顺序理解错误，模型产生了错误元素值

把模型当前输出和按 `atom_id` 数字后缀正确排序后的结果对比，可以看到：

- 在 90 个分子中，至少有 `31` 个分子的第 4 原子取值不一致

几个非常直观的例子：

#### `TR001`

- 模型输出：`cl`
- 正确第 4 原子：`c`

原因：

- 模型实际上拿到了 `TR001_12`
- 正确应该拿 `TR001_4`

#### `TR028`

- 模型输出：`c`
- 正确第 4 原子：`br`

前 6 个原子按编号顺序是：

- `TR028_1 = c`
- `TR028_2 = c`
- `TR028_3 = c`
- `TR028_4 = br`
- `TR028_5 = br`
- `TR028_6 = cl`

因此这个分子本应为 `br`，而不是 `c`。

#### `TR053`

- 模型输出：`h`
- 正确第 4 原子：`c`

这也解释了为什么模型最终结果里会出现不该出现的 `h`。

#### `TR149`

- 模型输出：`c`
- 正确第 4 原子：`s`

#### `TR234`

- 模型输出：`c`
- 正确第 4 原子：`n`

#### `TR450`

- 正确第 4 原子应为 `f`

这类分子在模型当前明细结果里没有把 `f` 反映出来，正是因为第 4 原子定位方式错了。

### 第五步：形成了“每分子一行”的中间结果，但这个中间结果已经带错

模型最终构造的是：

- `molecule_id + 第4原子element`

的明细表。

但由于上一步的原子顺序理解错误，这个中间表并不是“正确明细但没汇总”，而是：

- 粒度不对
- 且其中相当一部分 `element` 值本身就错

当前预测去重后只剩：

- `c`
- `cl`
- `h`
- `o`

而正确集合应为：

- `c`
- `br`
- `cl`
- `s`
- `o`
- `n`
- `f`

这意味着：

- 多了不应出现的 `h`
- 少了 `br / s / n / f`

因此不能把本题简单归因为“忘了去重”。

### 第六步：未执行 tally/去重收敛，直接提交

最终在 `answer` 阶段提交了 90 行二列表，row_count=90。

这一步确实是失败的直接触发点，但不是唯一错误。更准确地说，本题同时存在两层问题：

1. 第 4 原子提取口径错了
2. 最后没有聚合到元素层面

## 七、正确答案为什么应该是标准答案中的 7 个元素

gold 只保留元素层面的输出，说明评测口径不是“逐分子明细”，而是“元素汇总结果”。

也就是说，本题最终应回到元素维度：

- 去掉分子粒度
- 输出第4原子可能出现的目标元素集合

因此标准答案是：

- `c, br, cl, s, o, n, f`

这里需要特别强调：

- 如果模型前面的“第4原子明细表”本身是正确的，那么最后做 `DISTINCT element` 基本就足够了。
- 但这次模型的明细表本身就已经有误，所以“只补一次去重”仍然无法得到 gold。

## 八、正确查询应该怎么写

可用伪代码表达：

```python
# 1) carcinogenic_molecules = parse_from_molecule_md(...)
# 2) for each molecule, sort atoms by numeric suffix of atom_id
# 3) take atom with order = 4
# 4) keep only carcinogenic molecules
# 5) result = sorted(unique(elements))

# 输出单列 element
```

关键点有两个：

- 第 4 原子必须按原子编号顺序定位，而不是按 CSV 当前行序
- 最后必须使用 `DISTINCT element` 或按 `element` 聚合

## 九、本次错误的本质总结

### 1. 输出粒度错位

模型停在“分子粒度中间表”，未收敛到“元素粒度最终表”。

### 2. 第 4 原子定位逻辑错误

模型把 `atom.csv` 的文件行序当成了原子顺序，没有按 `atom_id` 的数字后缀排序，导致大量分子的第 4 原子元素被取错。

### 3. 文本抽取致癌集合存在噪声

`molecule.md` 中大量“修订叙述”会使集合膨胀，进一步放大明细输出。

### 4. 缺少最终结果模式检查

题目关键词 `tally` 应触发“聚合/汇总”动作，但模型未执行。

### 5. 提交前未对齐 gold 形状

提交为 2 列 90 行，而 gold 是 1 列 7 行，模式差异明显。

## 十、改进建议

### 1. 把“中间表”与“提交表”强制分离

中间表可保留分子维度，但提交前必须显式聚合到题目要求粒度。

### 2. 原子位次必须按 `atom_id` 后缀排序

对 `TR001_4` 这种原子编号，必须先解析出数字后缀，再定位第 4 原子；不能直接依赖 CSV 文件当前顺序。

### 3. 对 `tally/count/aggregate` 关键词加规则

遇到这类词，默认执行 `group by` 或 `distinct` 收敛。

### 4. 文本修订场景增加去噪策略

对“先否后改”的叙述建立状态机，避免重复或误收录。

### 5. 提交前做输出形状校验

自动检查列数、行数、粒度是否与任务类型匹配。

## 十一、结论

`task_379` 的失败不能只概括为“没做最后一步聚合”。

更准确的说法是：

- 模型先把一部分分子的第 4 原子取错了
- 然后又把分子明细直接提交，没再收敛到元素集合

因此本题同时存在“原子位次错误”和“输出粒度错误”两层问题。正确输出应为 7 个元素：`c, br, cl, s, o, n, f`。

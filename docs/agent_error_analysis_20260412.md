### 2.2 缺陷类型 A：目标语义被“看起来相关”的中间字段替代

- 命中 Task ID：`25, 80, 89, 163, 180, 200, 379`
- 对应失效环节：`Schema Linking` 为主，常伴随 `Reasoning` 末端漂移。

这一类任务的共同特征是：Agent 并非没有找到相关表、相关记录，甚至中间结果已经非常接近 gold，但最终取值字段、排序字段、计数对象或输出维度落错了层级。

典型表现：

- `task_25`
  - 题目要找可解释的最小活动成本，模型却直接把 `budget.spent` 当最终成本口径，拿到一批并列的 `0.0` 活动。
  - 这不是“没算出来”，而是把一个可能只是预算表状态字段的值，错误抬升成最终业务答案。
- `task_80`
  - 模型已经通过 `qualifying.csv` 找到相关 `driverId`，但最终取的是 `qualifying.number`，而不是 `drivers` 主档中的号码。
  - 本质是字段来源没有锁定主表，属于“候选人找对了，答案字段取错了”。
- `task_89`
  - 题目中的 `ranked second` 应落到 `rank` 字段，模型却按 `position=2` 取值，最终提交 `+14.925` 而非 gold 的 `+16.445`。
  - 这是典型的语义近邻字段混淆。
- `task_163`
  - 模型算对了总额 `175.39`，但最终输出成预算 `category`（`Food/Advertisement`），而题目要的是事件层 `type`（`Meeting`）。
  - 说明它有计算能力，但没有稳定维护“最终答案字段属于哪一层”。
- `task_180`
  - 题目明确是 `more than 29.00 per unit`，模型却写成 `Price > 29.00`，把单价条件误读成总价条件，直接放大候选人群。
- `task_200`
  - 模型中间已经找对目标分子，但最后把“要数目标元素原子数”漂移成了别的计数对象，属于答案拼装时的语义脱锚。
- `task_379`
  - 模型把“第 4 个原子”理解成文件中的第 4 行附近原子，而不是按 `atom_id` 数字后缀排序后的第 4 个原子，导致元素值源头就错。

这一簇说明，当前 Agent 的主要风险不是完全失联，而是容易把“中间可用字段”误当“最终答案字段”。一旦任务里存在多个看起来都合理的近义字段，模型缺少稳定的字段归属判断。

### 2.3 缺陷类型 B：聚合公式与样本集口径漂移

- 命中 Task ID：`169, 200, 249, 379`
- 对应失效环节：`Reasoning` 与 `Validation` 并发失效。

这一类问题的共同点是：模型能把数据取出来，但在最后的聚合、平均、去重、计数对象上发生漂移，导致结果偏离 gold，且常常没有自我察觉。

典型表现：

- `task_169`
  - 模型成功筛到 SME 用户和 2013 年数据，甚至修复了首次 Python 超时，但最终公式写成 `SUM(Consumption)/12`，而不是题意需要的平均口径。
  - 结果从正常量级的 `459.956...` 膨胀到 `82027220.304...`，属于“执行对了，公式错了”。
- `task_249`
  - 模型第一次因 `NoneType` 聚合报错，随后为了修复错误，使用了 `if upvotes is not None and age is not None`。
  - 这一步虽然解决了程序错误，却把 `AVG(UpVotes)` 和 `AVG(Age)` 强行绑到同一交集样本，破坏了两个指标应独立聚合的语义。
- `task_200`
  - 中间能定位目标分子，但最终在“count 哪个对象”上发生偏移，说明最后一步的计数合同没有被显式固定。
- `task_379`
  - 模型先产出“每个分子一行”的明细，再直接提交，没有继续做题目要求的 `tally / distinct` 收敛。
  - 这类问题不是单纯少做一步，而是没有把“中间表”和“提交表”明确区分。

这一簇暴露出的不是单纯数学错误，而是“聚合口径没有被显式管理”。Agent 会在取数正确后，把最后一步留给临场拼装，结果一旦出现 NULL、去重、计数对象、分母等细节，就容易漂。

### 2.4 缺陷类型 C：工具报错后的恢复停留在执行层，没有重审语义

- 命中 Task ID：`80, 89, 200, 249, 344, 352, 379`
- 对应失效环节：`Tool Usage` 为主，并反向放大 `Schema Linking` / `Reasoning` 失误。

这一簇的共性不是“工具报错”本身，而是报错后的恢复策略过于表层：模型只是在 SQL 和 Python 之间切换，或者补一个语法错误，但没有重新审视“题意是否理解对了、当前路径是否仍然正确”。

典型 trace 证据：

- `task_80`
  - 模型对 `csv/qualifying.csv` 调 `execute_context_sql`，SQL 为 `SELECT * FROM qualifying WHERE raceId = 903 ...`，工具失败后切到 Python。
  - 但切换后修复的是“怎么读取 CSV”，不是“号码究竟来自哪个表”，所以最终仍答错字段。
- `task_89`
  - 对 `csv/results.csv` 调 SQL 失败后，模型改用 Python；执行方式对了，但仍沿用错误语义 `position=2`，没有重审 `ranked second` 的字段映射。
- `task_249`
  - SQL 路径失败后转 Python，第一次 Python 因 `NoneType` 崩溃；第二次虽然跑通，却是通过错误的交集过滤修出来的。
  - 说明恢复只围绕“让程序能跑完”，没有回到“指标口径是否独立”。
- `task_344`
  - 对 `csv/Laboratory.csv` 多次尝试 SQL 查询，工具边界一开始就错，后续即使切到 Python，也一直在 FG 阈值和统计粒度上摇摆。
- `task_352`
  - 先对 `csv/event.csv` 调 SQL，后续 Python 又出现 `re` 未导入；模型在修脚本细节，却没有尽快把“关系抽取规则”冻结下来。
- `task_379`
  - 对 `csv/atom.csv` 先调 `execute_context_sql`，再调 `inspect_sqlite_schema`，都不适配文件类型。
  - 后续即便 Python 成功运行，原子顺序理解仍错，导致程序“能跑”和语义“跑对”完全脱节。

这一簇说明，当前 Agent 的工具恢复机制更像“故障绕行”，而不是“语义复盘”。如果没有强制它在报错后重写一次问题合同，模型往往会把原本就偏掉的语义继续带进新的工具实现里。

### 2.5 缺陷类型 D：拿到关键证据后仍无法收敛到可提交答案

- 命中 Task ID：`173, 344, 352, 396`
- 对应失效环节：`Reasoning` 为主，`Validation` 和终态控制同时缺位。

这是本批次最伤覆盖率的一类问题。几道任务都不是“完全没有线索”，而是在关键证据已经出现之后，Agent 仍继续验证、切源、试探规则，最终把 step 用尽。

共性特征：

- 4 个任务全部 `answer = null`
- 4 个任务全部跑满 `64` 个 step
- trace 中存在明显的重复工具调用、空转或 repair 后继续试探现象

典型表现：

- `task_173`
  - 模型已经确认 `yearmonth.csv` 中存在 `201306`，也读到了 `gasstations.json` 的国家域，但仍执着于补一条“201306 -> GasStationID -> Country”的完整明细联结。
  - 问题在于该题上下文本来就不给闭合证据链，Agent 却没有“最小可答”降级策略。
- `task_344`
  - 模型先后在 SQL 边界、FG 阈值、记录级/患者级统计之间反复横跳。
  - 它意识到前面的口径不稳，但没有形成一个冻结规则后继续推进的终态策略。
- `task_352`
  - 模型一度已经逼近正确的 `event_id` 和候选 `budget_id`，却把“大窗口内共现”误当关系，再退回全局试探，最后没交卷。
- `task_396`
  - 模型读了 `knowledge.md`、`publisher.json` 和长文本后，已经形成了身高、publisher、角色映射三块中间结果，但始终没有跨出最后的 join 与比例计算。
  - 这类失败不是不会抽取，而是没有“证据够了就提交”的门槛。

这一簇说明，当前 Agent 缺少一种很关键的能力：在复杂题里判断“现在已经足够回答了”。一旦没有这个机制，模型会天然偏向继续找证据，而不是收敛答案。

### 2.6 缺陷类型 E：提交前缺少答案合同校验

- 命中 Task ID：`25, 80, 89, 163, 169, 180, 379`
- 对应失效环节：`Validation` 为主，是多个簇的共同放大器。

这一类不是上游理解完全错误，而是明明已经出现明显异常，提交前却没有任何守门环节把它拦下来。

典型表现：

- 单值题提交成多行并列集合，如 `task_25`
- 题目只要单列，却提交多余列，如 `task_80, 89, 180`
- 明细中间表未聚合成最终粒度，如 `task_379`
- 数量级明显失真却未回检，如 `task_169`
- 候选规模异常放大却未回看筛选条件，如 `task_180`

从 trace 看，当前 Agent 更像是在“算到一个可打印结果”后就直接 `answer`，而不是在 `answer` 前执行一轮“是否符合题目合同”的低成本检查。

## 3. 深度根因剖析 (Root Cause)

### 3.1 语义锚点缺失，导致最终答案字段长期漂浮

这批失败任务里，最核心的问题不是取不到数据，而是 Agent 没有稳定维护“最终答案到底属于哪一层语义”的能力。它会在事件层、预算层、结果层、主档层之间来回借字段，一旦存在多个近义字段，就容易被“看起来也说得通”的中间字段吸走。

这背后反映出两个系统性缺陷：

- 缺少字段归属与 provenance 约束，模型不知道 `type` 是事件类型还是预算分类，`number` 应来自事实表还是主档表。
- 缺少题面术语到字段/公式的硬映射，像 `ranked second`、`per unit`、`tally` 这类短语仍靠临场猜测。

### 3.2 中间分析与最终提交脱节，最后一步经常“临门一脚踢偏”

不少任务并不是前半程完全错误，相反，中间分析已经非常接近 gold，但最后一步缺少明确的答案合同，导致：

- 聚合对象变了
- 去重没做
- 粒度停在明细层
- 单值题没有唯一化
- 正确总额配错维度

也就是说，当前 Agent 在“生成中间证据”上比“收敛最终答案”更强。系统没有强制它在提交前重新声明：

- 目标列是什么
- 行数应该是一行还是多行
- 当前结果是否还带冗余列
- 我数的到底是元素、分子、记录还是用户

### 3.3 报错恢复机制只修执行，不修语义

这批 trace 的一个高频模式是：

1. 先用错工具或脚本报错
2. 再切到另一个执行器
3. 程序跑通
4. 语义仍旧错误

这说明恢复机制的目标是“让代码跑完”，而不是“让答案跑对”。工具失败本应成为一次语义反思触发器，但当前系统没有把这一步制度化，因此模型会把原本错误的逻辑完整搬运到新的执行路径中。

### 3.4 复杂任务缺少“最小可答”与“终态冻结”策略

`task_173, 344, 352, 396` 说明另一个系统性短板：Agent 在复杂、多源、半结构化题里无法判断何时应该停下来提交。

常见症状是：

- 明明关键键值已经拿到，仍继续补证据
- 明明规则已经有候选版本，仍不断换口径
- 明明中间表已可 join，仍停留在解析阶段

这类问题本质上不是算力不够，而是缺少终态控制。系统没有给模型一个清晰的门槛：当主键、目标字段和结果形状都已满足时，应优先提交，而不是继续追求一条过度完美的证据链。

### 3.5 缺少低成本 sanity check，使小错被放大成最终错误

很多错误其实可以被极便宜地拦截：

- 月均值怎么会高到 `8.2e7`
- 单值题为什么输出 12 行
- 题目只要 `Consumption`，为什么提交 `CustomerID, Consumption`
- 条件过滤后为什么候选规模突然到 153

这些都不需要额外复杂推理，只需要一个轻量级提交前检查器。当前系统缺少这层守门，导致本可修复的小偏差直接进入最终答案。

## 4. Agent 优化建议 (Action Items)

### 4.1 Prompt / CoT 优化

- 强制引入“最终答案合同”步骤，在真正提交前明确写出：
  - 目标列
  - 目标粒度
  - 预期行数
  - 聚合对象
  - 分母/去重/NULL 策略
- 对高风险短语增加强制复核提示：
  - `per unit`
  - `ranked second`
  - `tally`
  - `type`
  - `contains`
- 在长链路任务中加入“最小可答路径”提示：
  - 先判断是否必须构造完整联结链
  - 若证据链无法闭合，优先提交 benchmark 可接受的最小答案
- 对报错恢复增加语义回顾模板：
  - 上一轮失败点是什么
  - 当前要修的是执行方式还是语义定义
  - 提交前是否需要重写一次查询合同

### 4.2 RAG / Knowledge 增强

- 增补术语到字段/公式映射字典：
  - `per unit -> Price / Amount`
  - `ranked second -> rank`
  - `tally -> distinct/count aggregation`
  - `contains X -> count atom occurrences of X` 或按题意指定计数对象
- 增补字段归属字典与主档优先级规则：
  - 编号优先来自主档还是事实表
  - `type/category/status` 分别属于哪一层实体
- 对半结构化文档新增关系抽取模板：
  - 禁止用大窗口共现替代真实关系
  - 先锁键，再抽值
  - 键值绑定后再做汇总
- 对多源任务补“主源 + 佐证源”说明，减少模型在多个文件间来回切换。

### 4.3 Tool / 工程层优化

- 增加文件类型到工具的路由守卫：
  - CSV/JSON/Markdown 不应被当作 SQLite schema 直接 inspect
  - 工具不适配时，应返回明确且可操作的替代建议
- 在工具报错返回里附带“可能的语义风险提示”，而不是只给执行失败：
  - 当前路径是否把 CSV 当 DB
  - 当前 SQL 是否遗漏主档回连
  - 当前修复是否可能改变样本集口径
- 增加 answer validator：
  - 列数/列名检查
  - 单值题唯一化检查
  - 明细/聚合粒度检查
  - 数量级与候选规模 sanity check
  - 多指标任务的独立样本集审计
- 增加长任务收敛控制：
  - 连续空转或重复调用同类工具时告警
  - 接近 `max_steps` 时强制进入“最小可答收敛模式”
  - 对已具备主键、目标字段、结果形状的任务触发兜底提交策略

## 结论

这 13 个失败任务说明，当前 Data Agent 的主要短板并不在“没有检索能力”，而在“没有把证据稳定转译成答案的制度化流程”。更具体地说，它在复杂任务里既容易把中间字段误当最终答案，又缺少在报错后重审语义、在提交前校验答案合同、在长链路场景里及时收敛的能力。

如果只继续提升模型自由推理能力，而不补上字段归属、聚合合同、工具路由和提交校验这几层工程化约束，这类错误仍会持续重复出现。相反，只要把这些环节补齐，当前 Agent 已经具备的取数和局部分析能力就能更稳定地转化成正确提交。

# Data Agent 截断设计评估报告

> 项目: kddcup2026-data-agents-starter-kit
> 分析日期: 2026-06-07

---

## 一、概览

本 data agent 中存在一个多层、多点的截断体系，覆盖了从工具调用输出、消息历史管理、到答案校验上下文构建的完整链路。经过全面代码审计，共识别出 **6 大类、18+ 处** 截断机制，分布在 10 个源文件中。

截断体系可分为以下几个层次：

| 层次       | 截断类型                 | 主要目的                         |
| ---------- | ------------------------ | -------------------------------- |
| SQL 查询层 | 行数限制 (`fetchmany`) | 控制数据库返回的数据量           |
| 工具输出层 | Token + 列表项数截断     | 防止单次工具输出撑爆上下文窗口   |
| 消息历史层 | 推理内容剥离 + 图片压缩  | 控制发送给模型的上下文长度       |
| 答案校验层 | 答案内容截断             | 控制校验器看到的上下文大小       |
| 数据目录层 | Token 预算 + Top-N 切片  | 控制 schema/文档预览大小         |
| Prompt 层  | 行为指令                 | 引导模型主动避免不必要的数据截断 |

## 二、各截断点详细分析

### 2.1 核心截断工具模块 (`tools/truncation.py`)

这是整个截断体系的基础设施模块，提供三个核心函数。

**`truncate_str(text, max_tokens=10000)`**

基于 Qwen3.5-35B-A3B tokenizer 做 token 级截断。当文本 token 数超过阈值时截断，并追加中文后缀 `"\n\n...（内容已被截断，返回过长。如未获取到所需信息，请尝试其他方式而非直接读取全部文档。）"`。

**`truncate_content(obj, max_str_tokens=2000, max_list_items=200)`**

递归遍历任意嵌套结构（str / list / dict），对字符串做 token 截断，对列表做条目数截断。当列表被截断时，会在末尾追加 `TRUNCATION_SUFFIX` 作为哨兵标记。

**`truncate_answer_content(answer, max_str_tokens=2000, max_list_items=200)`**

专门用于答案 dict 的截断。保留 `columns` 字段不做截断，对 `rows` 和其他字段调用 `truncate_content`。

**潜在问题：**

- **默认参数不一致**：`truncate_str` 的默认 `max_tokens=10000`，而 `truncate_content` 调用 `truncate_str` 时传入 `max_str_tokens=2000`。虽然 `truncate_str` 未被外部直接调用，但这两个默认值之间的矛盾容易在未来维护时引发混淆。
- **`TRUNCATION_SUFFIX` 是纯中文**：虽然 `prompt2.py` 中明确训练模型识别 `内容已被截断` 关键词，但如果使用中文能力较弱的模型，可能无法正确理解这个截断标记。
- **`TRUNCATION_SUFFIX` 作为字符串混入列表**：`truncate_content` 在 list 末尾追加一个中文字符串哨兵，但该 list 可能原本包含 dict 或 list 元素。下游消费者如果假设列表元素类型一致，在遍历到哨兵时可能出错。

### 2.2 Token 工具 (`token_utils.py`)

提供 `count_tokens()` 和 `truncate_by_tokens()` 两个底层函数，使用 Qwen3.5-35B-A3B tokenizer（优先加载本地 assets 目录，回退到 HuggingFace 在线模型）。线程安全（双重检查锁 + `threading.Lock`）。

**潜在问题：**

- **Tokenizer 与实际推理模型不匹配**：项目可使用 GPT-4.1-mini 等非 Qwen 模型做推理，但 token 计数始终基于 Qwen tokenizer。不同模型的 tokenizer 差异可能导致截断位置不准确——对 Qwen 来说刚好截断到 10000 token 的文本，对 GPT-4 可能是 8000 或 12000 token。
- **`truncate_by_tokens` 在 decode 时使用 `skip_special_tokens=True`**：如果原文本包含特殊 token 对应的字符序列，decode 后可能丢失或改变内容。
- **逐字符串 token 计数性能开销大**：`truncate_content` 对每个字符串都调用一次 `count_tokens()`（即一次 `tokenizer.encode()`）。对于包含数百个短字符串单元格的 SQL 结果表，这意味着数百次独立的 encode 调用，没有批处理优化。

### 2.3 SQL 查询行截断

#### 2.3.1 Probe Query (`tools/probe_engine.py` + `tools/registry.py`)

`execute_probe_query` 使用 `fetchmany(limit + 1)` 的哨兵行技术：多取一行用于判断是否截断，但只返回 `limit` 行。返回结果包含 `truncated: true/false` 标志。

- **Registry 层硬上限**：`registry.py:630` 处 `limit = min(int(...), 200)`，强制限制单次 probe 查询最多 200 行。
- **LLM 工具 schema 默认值**：`langgraph_tools.py` 中 `ExecuteProbeQueryArgs.limit` 默认为 `5`，描述中标注 "max 200"。
- **最终提交时绕过**：通过 `submit_tool_result` 路径执行时，`limit=None`（无限制），取回全部数据。

**潜在问题：**

- **Schema 描述与代码实现不匹配**：工具描述说 "max 200"，但 registry 层已经用 `min(..., 200)` 强制限制，LLM 传入 `limit=1000` 也会被截到 200。这是安全设计，但 schema 中未声明 "hard ceiling"。

#### 2.3.2 Context SQL (`tools/sqlite.py` + `tools/registry.py`)

`execute_read_only_sql` 同样使用 `fetchmany(limit + 1)` 哨兵行模式。

- **Registry 层无硬上限**：`registry.py:597` 处 `limit = int(action_input.get("limit", 200))`，**没有**像 probe query 那样做 `min(..., 200)` 的上限保护。
- **最终提交时绕过**：`submit_tool_result` 路径同样设 `limit=None`。

**潜在问题（Bug 风险高）：**

- **模型可请求任意行数**：LLM 可传入 `limit=999999`，registry 层不会拦截。虽然 `truncate_content` 会在之后把列表截到 200 项，但 SQL 执行阶段会先把 999999 行全部 `fetchmany` 到内存中，可能造成内存溢出或严重超时。这与 probe query 的处理形成明显不一致。

#### 2.3.3 两者对比

| 特性         | Probe Query (DuckDB)        | Context SQL (SQLite)      |
| ------------ | --------------------------- | ------------------------- |
| 默认 limit   | 200 (registry) / 5 (schema) | 200 (schema + registry)   |
| 硬上限       | `min(..., 200)` ✅        | **无** ❌           |
| 提交时 limit | `None`                    | `None`                  |
| 截断标记     | `truncated: true/false`   | `truncated: true/false` |
| 哨兵行技术   | ✅                          | ✅                        |

### 2.4 工具输出截断 (`tools/registry.py: format_result`)

所有工具返回给 LLM 的结果都经过 `format_result()` 统一截断：

```python
def format_result(self, action, result):
    payload = {"ok": result.ok, "content": result.content}
    if result.answer is not None:
        payload["answer"] = truncate_answer_content(
            result.answer.to_dict(),
            max_str_tokens=self.tool_config.max_output_tokens,  # 默认 10000
            max_list_items=self.tool_config.max_list_items,      # 默认 200
        )
    if action != "submit_tool_result":
        payload["content"] = truncate_content(
            payload["content"],
            max_str_tokens=self.tool_config.max_output_tokens,   # 默认 10000
            max_list_items=self.tool_config.max_list_items,       # 默认 200
        )
    return payload
```

**两个分支：**

1. **`result.answer` 截断**：仅当工具返回包含终端答案时（即 `submit_tool_result`），对 `answer` 字段做 `truncate_answer_content`。
2. **`content` 截断**：除 `submit_tool_result` 外的所有工具，对 `content` 字段做 `truncate_content`。

**潜在问题：**

- **双重截断**：工具输出时 `content` 被截断一次（`format_result` 中），之后答案提交校验时又被 `_submitted_answer_for_validator_context` 截断一次。两次截断独立进行，校验器和 agent 看到的可能是不同截断版本的数据。
- **`submit_tool_result` 的 `content` 未截断**：该工具的 `content` 是一个小的状态 dict（如 `{"status": "submitted"}`），通常不大。但代码中没有对其大小做任何保护，如果未来该 dict 变大，可能泄漏大量 token 到上下文中。
- **每个字符串 token 阈值过高**：`max_str_tokens=10000` 意味着单个字符串字段可达约 40KB 文本。对于表格数据中的单元格来说，这个阈值几乎不会触发。但如果某个工具返回了一个包含大段文本的字段，10000 token 仍然可能占据大量上下文空间。

### 2.5 消息历史截断 (`agents/langgraph_runtime.py`)

#### 2.5.1 推理内容剥离 (`_prepare_messages_for_model`)

在每次调用模型前，对消息历史中的 AI 推理内容（reasoning/thinking）进行裁剪：

- **`strip_reasoning_history=True`**：剥离所有 AI 消息中的 reasoning 内容。
- **`reasoning_history_limit=N`**：保留最近 N 条 AI 消息的 reasoning 内容，更早的全部剥离。
- **`reasoning_history_limit=None` + `strip_reasoning_history=False`**：保留全部 reasoning 历史。

实现方式是逆序遍历消息列表，对每个 `AIMessage` 检查是否包含 reasoning 内容，根据剩余配额决定是否剥离。

#### 2.5.2 图片消息压缩 (`_compress_used_image_messages`)

在每次调用模型前，将消息历史中已"使用过"的图片消息替换为纯文本摘要：

```
Compressed image observation:
Images:
  1. path=/some/path.png, detail=auto
Assistant note after viewing:
<truncated note, max 600 chars>
```

- **`compress_used_image_messages=True`**（默认开启）
- **`compressed_image_note_chars=600`**（字符级截断，非 token 级）
- 只压缩**其后存在 AI 回复**的图片消息。如果图片之后没有 AI 消息（比如最新上传的图片），则保留原始图片字节。

**潜在问题：**

- **字符级 vs Token 级不一致**：图片 note 用字符截断（`_truncate_text_by_chars`），而工具输出用 token 截断。600 个字符的中文文本可能对应 800+ token，而 600 个字符的英文文本约 100-150 token，信息密度差异大。
- **图片 note 使用 `"..."` 而非 `TRUNCATION_SUFFIX`**：与工具输出的截断标记不统一，模型可能无法一致地识别截断发生。
- **最新图片永远不会被压缩**：如果 agent 在查看图片后立即调用模型但该图片尚未得到 AI 回复，则完整图片字节会一直保留在上下文中。随着对话变长，这些未压缩的图片可能占据大量 token。

#### 2.5.3 歧义分析预览截断 (`analysis_preview`)

```python
analysis_preview = json.dumps(result, ensure_ascii=False)[:500]
```

歧义分析结果在写入 `StepRecord.assistant_message` 时被硬截断为 500 字符。完整结果仍保留在 `state["ambiguity_analysis"]` 和 `tool_results` 中。

**潜在问题：**

- **无截断标记**：`[:500]` 切片后没有追加 `"..."` 或任何标记。查看 trace 日志时，可能误以为分析结果只有 500 字符。
- **可能截断在 JSON 中间**：500 字符处可能正好在 JSON 字符串中间，产生无效 JSON。虽然是展示用途，但如果有下游工具尝试解析该 preview 会出错。
- **硬编码不可配置**：500 字符是写死在代码中的，无法通过 YAML 配置调整。

### 2.6 答案校验截断 (`agents/langgraph_runtime.py` + `agents/answer_validator.py`)

当 agent 通过 `submit_tool_result` 提交答案后，系统会调用答案校验器（answer validator LLM）。校验器看到的答案经过截断：

**截断链路：**

1. `langgraph_runtime.py:1854` 调用 `_submitted_answer_for_validator_context()`，使用 `truncate_answer_content` 截断答案。
2. 阈值来自 `ToolConfig`：`max_str_tokens=10000`, `max_list_items=200`。
3. 通过 `answer_dict_for_validator != answer_dict_full` 判断是否发生了截断。
4. 截断标志 `answer_truncated` 传递给校验器，校验器在 prompt 中被告知："The JSON below is a truncated validator-context preview..."

**校验器端的前处理：**

```python
# answer_validator.py:299
if answer["rows"] and answer["rows"][-1] == TRUNCATION_SUFFIX:
    answer["rows"].pop()
```

校验器在构建 prompt 前，会尝试移除 rows 列表末尾的 `TRUNCATION_SUFFIX` 哨兵。

**潜在问题（设计张力）：**

- **校验器面临矛盾指令**：校验器 system prompt 的 Rule 9 严格要求"提交的答案不得使用 LIMIT 或截断"，但同时校验器自己接收到的就是一个被截断的答案预览。校验器必须区分"预览被截断是因为上下文限制"和"agent 的查询本身使用了 LIMIT"。这种区分对 LLM 来说容易混淆，可能导致误判。
- **哨兵移除逻辑脆弱**：只检查 rows 的**最后一个元素**是否等于 `TRUNCATION_SUFFIX`。如果 `truncate_content` 的实现变化导致哨兵不在末尾，则不会被移除。
- **深比较判断截断**：`answer_dict_for_validator != answer_dict_full` 依赖 dict 的深比较。由于 `truncate_answer_content` 总是创建新的 dict/list，值相等时比较结果为 False（未截断），值不等时为 True（已截断）。但如果某些单元格值在 `truncate_by_tokens` 的 encode→decode 过程中发生了微小的文本变化（如特殊字符丢失），即使没有真正截断也可能报 `truncated=True`，导致误报。

### 2.7 数据目录构建截断 (`inspectors/semantic_catalog.py`)

#### 2.7.1 文档预览截断

```python
is_truncated = token_count > budget.max_doc_tokens  # 默认 500 tokens
"preview": truncate_by_tokens(text, budget.max_doc_tokens) if is_truncated else text
```

非 `knowledge.md` 的文档在目录中只保留 500 token 的预览。`knowledge.md` 特殊处理，全文存储在 `"content"` 字段中。

**潜在问题：**

- **`knowledge.md` 无大小保护**：如果 `knowledge.md` 文件非常大（如数 MB），其全文会被加载到目录结构中，最终可能通过 schema 传递给模型，占用大量上下文。

#### 2.7.2 Top-N 相关性切片

```python
"relevant_assets": sorted(..., reverse=True)[:10],
"relevant_fields": sorted(..., reverse=True)[:20],
```

目录构建时，根据与问题的 token 重叠分数排序，只保留 top 10 assets 和 top 20 fields。

**潜在问题：**

- **评分算法过于简单**：仅基于 query token 与 asset/field token 的集合交集大小打分（`score = len(query_tokens & tokens)`）。这种纯词袋匹配的召回质量有限，可能漏掉语义相关但词汇不同的字段。
- **硬编码不可配置**。

#### 2.7.3 JSON 数组采样

```python
for item in value[:20]:  # 只扫描前 20 个元素
```

JSON 文件的数组字段在推断 schema 时只采样前 20 个元素。

**潜在问题：**

- 如果 JSON 数组的前 20 个元素不具有代表性（如后续元素包含额外的字段），目录中的 schema 描述将不完整。

#### 2.7.4 关系推断 Distinct 值上限

```python
MAX_RELATION_DISTINCT_VALUES = 200_000
```

关系推断时，每个字段的 distinct value 数量上限为 200,000。超出时设置 `capped=True`，关系置信度降低 0.05。这是一个性能安全阀，设计上合理。

### 2.8 歧义分析器截断 (`agents/ambiguity_analyzer.py`)

#### 2.8.1 知识文档 Token 预算

```python
def _build_knowledge_listing(knowledge_docs, max_tokens=2048):
```

所有知识文档共享 2048 token 的总预算。采用贪心分配策略：先出现的文档优先消耗预算，后续文档可能因预算耗尽而被完全跳过（`if remaining <= 0: break`）。

**潜在问题：**

- **分配不公平**：文档顺序决定优先级。如果第一个文档特别大，后续文档可能被完全丢弃，且无任何日志警告。
- **Wrapper 开销估算不精确**：`max(len(asset) // 4 + 10, 20)` 是基于字符数的粗略估算，不是精确的 token 计数。

#### 2.8.2 Schema 字段数上限

```python
max_fields = 200
```

传递给歧义分析器的 schema 信息最多包含 200 个字段。超出后显示 `"... (N more fields omitted)"`。

**潜在问题：**

- **按顺序截断，无相关性排序**：字段按 schema 中的出现顺序处理，而非按与问题的相关性排序。后面的 schema 可能所有字段都被省略。
- **硬编码不可配置**。

### 2.10 Prompt 层截断引导

System prompt 中包含两类截断相关指令：

**防止 agent 主动截断数据：**

> "Do not apply a top-N, LIMIT, or row truncation unless the question explicitly asks for a limited number of rows."

**引导 agent 识别并应对系统截断：**

> "If any observed output contains `...`, `[truncated]`, `内容已被截断`, or looks like a preview/table display, treat it as incomplete evidence and rerun a targeted tool call to print full JSON."

这构成了一套"截断意识"机制：agent 被训练为在看到截断标记时，主动重新获取完整数据。

## 五、优化建议

### 5.1 紧急修复

**为 Context SQL 添加 limit 硬上限**

参照 probe query 的做法，在 `registry.py:597` 处增加上限保护：

```python
# 当前
limit = int(action_input.get("limit", 200))

# 建议
limit = min(int(action_input.get("limit", 200)), 10000)  # 或其他合理上限
```

**为 `knowledge.md` 增加大小保护**

在 `semantic_catalog.py` 的 `_read_document_schema` 中，对 `knowledge.md` 也做 token 级别的大小检查，超过阈值时记录警告并在目录中存储截断版本。

### 5.2 中期改进

**统一截断单位**

建议将图片 note 的字符截断改为 token 截断，与工具输出保持一致。同时统一截断标记格式，使用 `TRUNCATION_SUFFIX` 替代简单的 `"..."`。

**为 `list_context` 和 `search_doc` 添加参数上限**

```python
max_depth = min(int(action_input.get("max_depth", 4)), 10)
page_size = min(int(action_input.get("page_size", 20)), 100)
```

**优化 token 计数性能**

对 `truncate_content` 中的字符串做批量 token 计数：先收集所有字符串，一次 batch encode 获取全部 token 数，再对超阈值的字符串做单独截断。

**缓解校验器矛盾指令**

在校验器 prompt 中更明确地区分"系统预览截断"和"查询层 LIMIT 截断"，例如提供结构化元数据（`original_row_count` vs `preview_row_count`），让校验器基于元数据而非截断内容判断。

### 5.3 长期优化方向

**引入全局 Token 预算管理**

当前各截断点使用独立阈值，没有全局上下文窗口预算。可考虑引入全局 token 预算管理器，根据当前消息历史长度动态调整各截断点的阈值，确保总输入不超出模型上下文窗口。

**截断策略可配置化**

将硬编码的限制（500 字符 preview、200 字段、2048 token 知识预算、top 10/20 切片等）抽取到 YAML 配置中，便于针对不同任务类型调优。

**双语言截断标记**

将 `TRUNCATION_SUFFIX` 改为中英双语格式，确保不同语言能力的模型都能识别：

```
"\n\n...[Content truncated / 内容已被截断]..."
```

**按相关性排序的 Schema 截断**

在歧义分析器中，将字段按与问题的相关性（而非出现顺序）排序后再截断，确保最相关的字段始终被保留。

鲜兴元 2026.05.18-2026.05.24 周报

鲜兴元 2026.05.18-2026.05.24 周报

一、本周工作内容

本周工作主要围绕 KDD Cup 2026 Data Agents 比赛 A 榜最后提交前的系统收敛展开。相比上周继续增加工具和节点，本周更强调“有效功能保留、低收益流程移除、关键错误修复”。整体工作包括测试 MemAgent 长文档抽取效果、完成过程校验 Agent、清理已经验证收益有限但增加运行时间的流程，以及整理最终版本相对 baseline 的改进报告。

1. 测试 MemAgent 效果，并在最终提交时移除工具入口

本周首先继续测试 MemAgent 在长文档任务上的效果。MemAgent 的目标是把较长的 Markdown / 文本文档通过规则抽取转成结构化 SQLite 表，再让主 Agent 通过 SQL 查询这些抽取结果。这个方向主要针对 task 396 这类长文档中包含大量相似记录、直接全文阅读成本较高的任务。

实现上，本周做了几轮改造：

  1. 将 MemAgent 从单纯的长文档摘要工具，重构为“模式提取 + 确定性 ETL 引擎”的结构。
  2. 增加文档结构分析、正则 / Python 抽取模式生成、修复循环和诊断信息。
  3. 增加 scripts/test_memagent_task396.py，专门用于测试 task 396 上的文档抽取效果。
  4. 后续又去掉题目集硬编码字段，把实现改成更通用的文档抽取引擎，并保留为 memagent_etl.py。

测试后发现，MemAgent 在复杂长文档任务上确实有一定潜力，尤其适合“文档中存在大量结构相似条目，需要先抽取成表再筛选 / 聚合”的情况。但它在当前 A 榜提交场景下也有明显问题：单次调用耗时较长，规则质量依赖模型输出，且会增加主 Agent 的工具选择复杂度。如果普通文档任务可以通过 lookup_doc_outline、read_doc、search_doc 和定向 Python 正则解决，直接引入 MemAgent 反而可能增加运行时间和不确定性。

因此最终提交前选择移除 MemAgent 的工具注册和提示词引用，只保留 ETL 实现与测试脚本，避免它进入正式 ReAct 工具链。这样既保留了后续继续研究长文档结构化抽取的代码基础，也避免在最后提交时引入额外耗时和不稳定因素。

2. 完成过程校验 Agent

本周完成了过程校验 Agent 的主体实现，并将其接入 LangGraph / runtime / runner / state / 配置体系。过程校验 Agent 的定位不是替代最终答案验证，而是在主 Agent 执行过程中检查推理路径是否已经偏离题意，尤其关注字段绑定、过滤条件、聚合口径、输出粒度和极值并列等高风险问题。

当前过程校验 Agent 主要有两类触发方式：

  1. 周期性校验：在工具调用若干步之后触发一次过程检查，当前提交配置中使用 checkpoint_model_interval: 10。
  2. 终结性校验：主 Agent 准备提交最终答案时，先经过过程校验，再进入最终答案验证或提交。

本周对过程校验 Agent 的提示词和规则做了多轮收紧。最开始只是让它指出可能的推理问题，后续逐步补充了更明确的检查项，包括：是否误删 0 或异常数值、是否错误排除重要数据、是否完成题目要求的聚合、极值题是否保留并列答案、最终输出是否符合题目粒度等。

为了避免校验节点自身导致流程卡死，最终提交配置中将重试次数控制得比较保守：retry_limit: 1。也就是说，如果过程校验发现高置信度问题，会给主 Agent 注入一条反馈，让它重新探查和修正；但如果重试后仍无法稳定通过，则放行，避免无限纠偏带来超时风险。

这部分是本周最主要的正向工程产出。它把之前主要依赖最终答案校验的方式，推进到“过程中也能发现明显错误路径”的阶段，为后续继续降低字段绑定错误、聚合错误和输出形状错误提供了基础。

3. 最终提交前移除低收益但增加运行时间的流程

本周也对已经测试过但收益不明显的流程做了清理。最主要的是在最终提交配置中关闭歧义分析节点：enable_ambiguity_analysis: false。

之前歧义分析节点希望在主 Agent 执行前识别题目中的歧义类型，并提前提示可能的解释空间。但从多轮实验看，这个节点对最终得分的稳定提升有限。一方面，它会额外增加模型调用和上下文内容；另一方面，如果分析结果过长或过早给出候选解释，主 Agent 可能会被不确定信息干扰，反而增加探索成本。

因此最终提交时选择关闭该流程，把运行预算集中留给数据 catalog、主 Agent 工具调用、过程校验和答案校验。同时，本周也继续清理了此前已经确认收益不稳定的旧流程，包括删除 enable_semantic_enrichment 相关代码和配置、删除前置的 build_document_context_node，让最终版本的执行链路更短、更可控。

最终提交配置还做了几项收敛调整：将 catalog_top_distinct_values 从 30 降到 5，减少前置 catalog 的体积；将过程校验间隔统一为 10 步；将过程校验重试限制为 1 次；同时保留工具输出截断上限和答案验证节点，保证提交版本在稳定性和耗时之间做折中。

4. 修复最终提交前发现的关键 bug

本周还修复了几个会影响主 Agent 观察结果和工具行为的问题。

第一个是 execute_probe_query 单查询返回重复的问题。之前为了兼容旧接口，单条 SQL 查询时既会在 results 列表中返回结果，又会把同一份 columns、rows、row_count 等字段复制到顶层。这会造成工具输出冗余，也容易让模型误读结果结构。本周删除了这层兼容返回，统一要求探针结果从 results 列表中读取，避免重复数据污染上下文。

第二个是文档标题静默截断的问题。此前文档 heading 在 catalog 和 read_doc 错误提示中会被静默截断到前 20 条。如果目标章节排在较后位置，Agent 可能根本看不到相关标题，也不会意识到标题列表被截断。本周移除了这类隐式截断，改为交给统一的 ToolRegistry.format_result 做输出长度控制，并在真正截断时明确标记，让 Agent 知道需要通过更精确方式继续读取。

此外，本周还调整了 search_doc 默认上下文、修正中文提示词翻译、更新工具描述与参数说明，并对测试用例做了同步修改。这些修复不一定直接体现在分数上，但能减少模型因为工具返回格式不清晰、文档目录不完整或提示词不一致而走错路径的概率。

5. 整理最终版本相对 baseline 的升级报告

提交后，本周整理了 improvement_report.md 和对应 PDF，用于作为附件发送给老师。报告主要梳理当前系统相对 baseline 的核心改进，包括过程校验器、答案校验器、Knowledge / Catalog 注入、Agent 工具链、工具输出截断、本地 tokenizer 缓存计数、LLM 请求参数调优、历史 reasoning 滑动窗口管理等内容。

周报中不再展开这份报告的细节，后续可直接将 improvement_report.md 或 improvement_report.pdf 作为附件提交。

二、本周学习内容与收获

本周最大的收获是进一步明确了最后提交阶段不能只看“功能是否更强”，还必须看“功能是否稳定、是否耗时可控、是否会干扰主 Agent”。MemAgent、歧义分析、语义增强等方向从能力上看都有价值，但在当前 A 榜任务和时间限制下，并不是所有能力都适合进入最终提交链路。

尤其是 MemAgent 的测试比较有代表性。它可以把长文档转换成结构化表，这个方向本身很有价值，但如果工具调用成本高、规则生成不稳定、主 Agent 又不一定能正确选择调用时机，那么短期内直接纳入正式工具集并不划算。相比之下，过程校验 Agent 虽然也会增加一次模型调用，但它的触发条件、反馈内容和重试次数都更可控，更适合作为最后提交版本中的稳定性补强。

另外，本周也更清楚地看到，很多错误并不是单一 prompt 能解决的。字段绑定、输出粒度、极值并列、数值是否应排除、文档标题是否可见，这些问题分布在工具返回格式、上下文组织、校验节点和最终答案验证之间。后续继续优化时，需要把它们当作一条完整链路来看，而不是只在某一个节点上不断加说明。

三、当前存在的问题

当前主要还存在以下问题：

  1. MemAgent 虽然保留了 ETL 实现，但还没有形成适合正式提交的稳定调用策略。特别是如何判断“何时值得抽取成长表”、如何降低规则生成失败率、如何控制单任务耗时，还需要继续实验。
  2. 过程校验 Agent 已经接入，但它本身仍可能出现过度谨慎或反馈不够精确的问题。目前通过限制重试次数降低风险，后续还需要根据错误任务继续打磨校验标准。
  3. 最终版本仍然存在一些低分任务，尤其是复杂长文档任务、极端任务和输出口径容易错的任务。这些问题说明系统在复杂证据链、文档理解和答案契约执行上仍有提升空间。
  4. 第二阶段可能涉及图像、视频等多模态数据，目前系统主要还是面向结构化数据和文本资料，视觉信息解析能力储备不足，需要提前准备。

四、下周计划

下周计划根据老师在微信群中的提醒，提前开始准备第二阶段内容。老师提到：“根据 A 榜的最终成绩，大家进第二阶段问题不大。这段时间针对第二阶段的内容提前准备起来。尤其是对图像视频等分析的技术。先找找相关资料学习学习。” 因此下周重点会从 A 榜提交后的代码收尾，转向第二阶段可能用到的技术调研和预研。

具体计划如下：

  1. 调研图像、视频和复杂文档分析技术。重点关注 OCR、版面分析、表格识别、图表理解、视频帧抽取、视觉问答、多模态大模型与结构化数据 Agent 的结合方式，提前判断哪些能力可能在第二阶段任务中用得上。
  2. 梳理当前系统中可以复用到多模态阶段的部分，例如任务路由、工具调用、过程校验、答案校验、输出契约和 trace 复盘机制；同时找出需要新增的视觉工具接口。
  3. 调研老师在群里发的“MIT：真实企业数据 SQL 智能体 Benchmark”。初步看，这一方向与 Spider 2.0 等真实企业级 Text-to-SQL benchmark 高度相关，核心特点是大规模 schema、真实企业数据、复杂元数据、SQL 方言、长上下文和多步查询工作流。它对后续比赛有参考价值，尤其能帮助我们学习 schema linking、metadata search、SQL agent 过程验证、多查询生成和结果校验方法。
  4. 进一步判断该 SQL benchmark 与 KDD Cup 第二阶段的关系。如果第二阶段仍以复杂数据分析为核心，它可以作为 SQL / 数据库 Agent 能力建设的参考；如果第二阶段更偏图像视频和跨模态证据融合，则它不能直接替代多模态能力，但其中关于复杂工作流拆解、元数据检索和自动校验的思想仍然可以复用。
  5. 继续复盘本周最终提交版本中的低分任务，尤其是长文档、极值并列、输出列名和多余列问题，把过程校验 Agent 后续应该强化的规则整理出来。
